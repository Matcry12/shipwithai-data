# Git Code Review - Best Practices.pptx
The document outlines best practices for code review, including guidelines for git branching, merging, and commit message formatting. It emphasizes the importance of following naming conventions, obtaining required approvals, and ensuring code quality and security. Additional recommendations include using appropriate coding standards, meaningful variable names, and leveraging tools like SonarQube for code inspection.

## Git Code Review - Best Practices.pptx
  * 1. 
[Best Practices for](https://www.slideshare.net/slideshow/git-code-review-best-practicespptx/251692859#1)Code Review Parveen Soni https://github.com/parveen-rx/ 
  * 2. 
[Git Branching Following shall be](https://www.slideshare.net/slideshow/git-code-review-best-practicespptx/251692859#2)the naming convention for branching while working in any Project: • Project: release-<version> • Sub-Project/Plugin: <main project abbreviation>-release-<version> • JIRA IDs: bug/<ticket no> story/<ticket no> imp/<ticket no> task/<ticket no> demo/<ticket no> • Commit Message in each commit in branch: <JIRA-ID> : <commit message>
  * 3. 
[Git Merging • Delete](https://www.slideshare.net/slideshow/git-code-review-best-practicespptx/251692859#3)the branch after merge • Unless required reviewers approve, don’t merge. • If there is something related to UI, make sure to get it approved by UI team. • Don’t merge if Git branching rules are not followed. • It is important to have JIRA ID in the commit to back-trace the commit to JIRA ID and have it linked with JIRA ticket. • Having JIRA ID in commit also make sure that team has followed the SDLC in the flow if the project undergo in the audit process. • Make sure to have proper meaningful commit message. 
  * 4. 
[Guideline to follow Check performance](https://www.slideshare.net/slideshow/git-code-review-best-practicespptx/251692859#4)aspect and ask dev to provide evidences if required. Example: nested loops with proper break and heavy use of contain/search in Collections. Ask for unit test for new code or update in existing code. Check code readiness and quality. Don’t review large code at a time. Ask for small PR changes for better review. Any configuration added must meets the application flexibility and configurability requirement. Check security aspect of the code like XSS or token exposure in URLs etc. 
  * 5. 
[Code Formatting and styling • Follow](https://www.slideshare.net/slideshow/git-code-review-best-practicespptx/251692859#5)Company SOP for coding guidelines (space, tab, brackets, CamelCase etc.) in JS or Java or any other tech. • Make sure variable names are meaningful and small. • Ensure meaningful logs are added for debugging purpose. • Common/re-usable code practice. • Code quality follow OOPS concepts. • Use SonarQube for code inspection. • Have SME review if don’t know the feature or changes.
