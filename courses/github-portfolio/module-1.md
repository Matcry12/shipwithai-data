# Module 1 — Why a Portfolio Beats a Resume Claim

Most developers treat GitHub as a backup drive for side projects. That mental model costs interviews. This module reframes GitHub as the central proof asset in a tech job search — the place where a resume claim becomes a verifiable fact.

---

## Lesson 1 — The Recruiter Funnel Is Three Steps, and GitHub Is the Verdict

When a recruiter in tech opens your application, the workflow is almost always the same: resume to establish baseline qualifications, LinkedIn to cross-reference dates and social proof, GitHub to decide whether the claims hold up.

The resume gets you onto the list. LinkedIn keeps you on it. GitHub removes you — or moves you forward.

"Recruiters now expect more than just a resume; they want rich, public evidence of skills, collaboration, and growth."[^1]

That expectation has shifted the weight of the hiring decision downstream. A polished one-page resume that says "proficient in React and Node.js" means little if the linked GitHub shows six empty repositories and a "hello world" project from three years ago. Conversely, a resume that is merely adequate can be rescued by a profile that shows consistent, working code.

The practical implication: every hour you spend word-smithing a bullet point on your resume returns less than the same hour spent cleaning up a pinned project with a clear README. The resume gets you a look. GitHub decides whether you get the call.

The funnel also has a LinkedIn step that is easy to underestimate. Stack Overflow's hiring manager guide notes that "LinkedIn, GitHub, and Stack Overflow are all sites where having an up-to-date profile will greatly help your job search."[^2] LinkedIn is where the recruiter forms a social impression; GitHub is where they form a technical one. The two are evaluated in sequence, not in isolation. A strong GitHub cannot fully compensate for a LinkedIn profile that looks abandoned, and vice versa.

**Action:** Draw the three-stage funnel on paper — resume, LinkedIn, GitHub — and honestly score your current state at each stage from 1 to 5. The lowest score is your highest-leverage fix.

## Lesson 2 — You Have 90 Seconds: Know What a Recruiter Actually Reads

Understanding that GitHub matters is not enough. You need to understand the specific reading order a recruiter follows, because that order determines where to invest your effort.

"In 2026's competitive job market, recruiters spend an average of 90 seconds scanning your GitHub."[^3]

Ninety seconds. That is not enough time to read code. It is barely enough time to form an impression. The reading order within those 90 seconds is predictable: profile photo and bio, pinned repositories, most-active project, README of that project. A recruiter who is still on your profile after 90 seconds is genuinely interested. Most are gone before the first repository is fully loaded.

The pinned repositories section is the highest-leverage real estate on your profile. "Next, they will look at the repositories you pin on your GitHub profile. The ones you pick should show your best work. You need to make sure that every project you pin on your GitHub has a README file. If you do not add a README, recruiters may not open it."[^4]

The README functions as a product landing page for your code. It answers the questions a recruiter is silently asking: What does this do? Why does it exist? Can I see it running? A recruiter will not read 300 lines of source to answer those questions. They will scan a README for 15 seconds, and if it does not answer them, they will close the tab.

The checklist a recruiter runs through mentally is short and consistent: Does the README clearly state what problem this solves? Does the project use technology relevant to the role? Is the commit history evidence of sustained work, or a single midnight push before the application was submitted?[^4]

That last point catches more developers than any other. A repository with one commit dated the night before the application arrived is not a portfolio project. It is a red flag.

**Action:** Open your current GitHub profile on a device you have not used recently and set a 90-second timer. Note exactly what you read. That is what a recruiter reads. List any question that went unanswered before the timer ran out.

## Lesson 3 — The Real Question Your Portfolio Must Answer

There is one question underneath all the recruiter behaviour described in the previous two lessons: *Can this person ship working software unsupervised?*

Not "do they know the syntax?" Not "have they heard of this framework?" Those questions are answered by a resume or a technical screen. The GitHub portfolio answers a harder, more predictive question about whether someone can take an idea from zero to deployed, make decisions when no one is watching, and produce something a user can actually touch.

"Your GitHub profile is your technical resume. A strong GitHub portfolio gets you interviews, even without a traditional degree."[^3]

The word "technical" in that sentence is doing real work. A traditional resume describes what you have done. A technical resume in the GitHub sense demonstrates how you do it. The difference is verifiable. Anyone can write "built a REST API with authentication" on a resume. A GitHub repository either has that working or it does not.

This framing clarifies what clarity means in a portfolio context. Clarity does not mean visual design or clever README formatting. It means a visitor can answer the question "does this person ship working software?" within the time they are willing to spend. "A coding portfolio is a curated collection of your programming projects that showcases your technical skills, problem-solving abilities, and coding style to potential employers or clients. For beginners transitioning into tech, a portfolio serves as tangible proof of your capabilities beyond what a resume can convey."[^5]

The phrase "tangible proof" is the standard to hold yourself to. Not impressive proof, not exhaustive proof — tangible. A single project with a live demo link, a clean README that explains the problem it solves, and a commit history showing the work happened over time does more for a job search than a dozen tutorial clones with no documentation.

Code golf — optimising for technical cleverness — is the wrong optimisation. A recruiter is not a compiler. They are asking a business question: will this person be able to work without hand-holding? Clarity of intent, working output, and evidence of sustained effort answer that question. Clever algorithmic solutions that require a PhD to evaluate do not.

**Action:** Pick your single strongest existing project. Write one sentence that answers the question "what problem does this solve and who would use it?" If you cannot write that sentence in under 30 seconds, your README is not doing its job yet. Rewrite the first paragraph of that README today.

## Module Summary

The recruiter pipeline for tech roles runs in three stages: resume establishes qualifications, LinkedIn provides social context, GitHub validates the technical claims. GitHub is the last gate before a recruiter decides to make contact, and it receives genuine scrutiny — an average of 90 seconds focused on the profile bio, pinned repositories, and the README of the most prominent project.

The entire profile is evaluated against one underlying question: can this person ship working software unsupervised? Clarity of problem statement, working output, and consistent commit history answer that question. Elaborate code or volume of repositories do not.

The practical shift this module asks for is a reallocation of job-search effort: treat your GitHub profile not as an archive but as a living product, maintained with the same intentionality you would bring to a portfolio you were handing directly to a hiring manager — because that is exactly what you are doing.
