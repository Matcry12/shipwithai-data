# Module 8 — GitHub as Your Evidence Locker

**Objective:** Turn everything you've built and judged into *proof* — a GitHub presence that demonstrates the one thing AI can't fake for you: that you understand, decided, and own your work. This is where Act 2 pays off the whole course. The skill is real; this module makes it *visible*.

> **Who this is for.** Everyone job-hunting or building a reputation — students, career-changers, juniors. No assumption you have an impressive GitHub yet; we're building one that proves judgment, not volume.

---

## Lesson 8.1 — The Signal Got Cheap

We opened the course (Module 1.4) with a hard truth; now we act on it. If anyone can generate clean, working-looking code in an afternoon, then **a GitHub full of clean, working-looking code proves almost nothing.** Reviewers know it. The old signal — "look, I can produce code" — got cheap the moment the machine could produce it too.

So the question your GitHub has to answer changed. It's no longer "can this person generate code?" It's **"can this person judge, decide, and own?"** — the three pillars from Module 1, the things the industry agrees AI *struggles* with: "system architecture, business logic, security, team collaboration… code quality assessment" — because "AI generates code, but humans must evaluate it" *(blog.teamtreehouse.com)*.

That reframes your whole GitHub. It's not a gallery of code — it's an **evidence locker for your judgment.** Every commit message, every pull request, every README is a chance to show the thing that's now scarce and valuable: that a thinking human was driving. The rest of this module is how to fill that locker on purpose.

And the payoff is concrete: the market pays a premium for exactly this — judgment, not raw output. Pure prompting, one 2026 career guide notes, "will become commoditized" *(authenticjobs.com)*; the candidates who "can architect, validate, and ship production code" are the ones who command more. Judgment is what's paid for.

> **⚠️ Dated callout — figures as of early 2026 (verify before you rely on them).** One career guide puts numbers on it: developers with strong AI-collaboration skills "command 15–25% premiums," junior-level roles in the "$80K–$100K" range, and the top "orchestrator" tier "30–40% premiums" *(authenticjobs.com)*. Salaries and premiums move fast and vary by market — treat these as one source's snapshot, not a promise. The durable point is the *direction*: the market rewards the judgment, not the typing.

## Lesson 8.2 — What Reviewers Actually Look For

Here's the encouraging part: recruiters genuinely look. "Recruiters might not explicitly tell you, but they absolutely click through on the project links… A deployed project that actually works **immediately** puts you above the pile of localhost screenshots and GitHub repositories" *(text2resume.com)*. The bar to stand out is lower than it feels — because most people don't do the things below.

What actually impresses, distilled from a 2026 hiring guide *(authenticjobs.com)*:

- **Product thinking** — "something that solves a real problem (even a small one)," features that show you thought about the user, "iteration based on feedback."
- **Technical judgment** — "clean architecture, not spaghetti code," sensible technology choices, "proper error handling and edge cases," "security basics (authentication, input validation)."
- **Proof you can ship** — "deployed and accessible (not just on localhost)," it "actually works (test it before sharing)," and "maintained over time (not abandoned after the demo)."

And the **portfolio red flags** that quietly sink applications *(authenticjobs.com)*:

- Only tutorial projects (build something *original*)
- Nothing deployed ("localhost doesn't count")
- Can't explain the code ("if you can't walk through it, don't include it")
- Obvious security issues ("exposed API keys, SQL injection" — exactly the Module 7.6 hygiene failures)
- No iteration ("everything looks like a first draft")

Notice none of these are about *how much* code you wrote. They're about whether the code shows a person who thought. A deployed, working, original project demonstrates "the complete software development lifecycle" and that you "know how to work with modern development tools" *(text2resume.com)* — which is the whole story you're trying to tell.

## Lesson 8.3 — Disclose the AI. Owning It Is the Flex.

The instinct is to hide that AI helped. **Do the opposite** — and understand *why* it's the stronger move. The consistent advice: "Be transparent about your process. Hiding that you used AI looks worse than owning it" *(authenticjobs.com)*. Everyone knows you used AI. Pretending you didn't reads as either dishonest or naïve; *showing how you supervised it* reads as exactly the 2026 skill employers want.

The framing that works, almost word for word *(authenticjobs.com)*:

> *"Built with Cursor and Claude. I architected the approach, guided the implementation, and validated all outputs for security and performance."*

Read that again — every verb is a *judgment* verb: architected, guided, validated. It says "I directed the machine," not "the machine did it." That's the Module 1 asset/liability line, turned into a portfolio sentence.

The same care applies in applications and interviews. There's a world of difference between **"I use AI to understand concepts faster"** and **"I use AI to write my code"** *(frontendmentor.io)*. The first signals strategic, modern, in-control. The second raises the exact red flag — "the AI suggested it" — that gets juniors filtered out (Module 1.3). Same honesty, opposite signal. Frame AI as your multiplier, never your author.

---

## Lesson 8.4 — The Locker Has to Survive the Interview

Here's the brutal, clarifying test that should govern what goes in your locker: **the interview is the one room the AI can't enter for you.** So the rule is non-negotiable *(frontendmentor.io)*:

> *"Portfolio projects should demonstrate your understanding, not AI's capabilities. If you can't explain it thoroughly in a technical interview, you shouldn't include it."*

And the sharp version of the test, from Module 3: *"Can you rebuild the core functionality from scratch without AI? If not, you don't understand it well enough to claim it as your work"* *(frontendmentor.io)*. Anything you can't explain or rebuild isn't an asset in your locker — it's a landmine waiting for the one interview question that exposes it.

This is also where Module 3's **"learn in public"** finally pays its hiring dividend. Every honest write-up — "here's a bug that confused me and how I figured it out," "here's why I changed what the AI suggested" — is simultaneously the thing that *forced* you to understand it (Feynman) and the artifact that *proves* you did. A learning trail is interview rehearsal you did months early, in writing, with receipts. The junior who's been narrating their reasoning in public walks into the interview already fluent in their own work.

## Lesson 8.5 — Filling the Locker (Concretely)

Translate all of the above into things you actually put on GitHub. None of this requires more code — it requires *visible thinking*.

**Write READMEs that show decisions, not just setup.** Beyond "how to run it," document *(authenticjobs.com)*:
- *Why* you chose certain approaches
- *What you changed* from the AI's suggestions (and why)
- Problems you hit and how you solved them
- What you'd do differently next time

**Show the before/after when you can.** "Your initial prompts and the raw AI output → your refinements and final code → why you made specific changes" *(authenticjobs.com)*. This single artifact proves judgment more vividly than anything else — it literally shows you out-judging the machine.

**Let your commits and PRs tell the story.** This is the Module 7 loop becoming a permanent record: commit messages that say *why*, PRs that explain your reasoning and what you verified, AI-assisted work honestly labeled. A reviewer scrolling your history should see a mind at work, not a dump of generated files.

**Deploy it, and keep it alive.** A live link beats a screenshot every time *(text2resume.com)*; an abandoned-the-day-after-the-demo repo is a red flag *(authenticjobs.com)*. One maintained, deployed, original project beats ten tutorial clones.

**Play to your strengths, vibe-code the rest — and say so.** A legitimate strategy: architect and hand-build the part that showcases *your* strength, vibe-code the supporting scaffolding, and document which was which *(text2resume.com)*. A backend-minded person builds the API by hand and vibe-codes the dashboard; that's not cheating, it's the modern workflow, *shown honestly.*

> *Developer-track note:* a couple of green-flag extras that punch above their weight — a meaningful test suite (it shows you think about correctness, Module 6.6), and a thoughtful issue or PR on someone else's open-source project (real collaboration evidence). We touch open source as an option in Module 9.

## Action — Audit and Upgrade One Repo

Don't rebuild your whole GitHub today. Take **one** project — the best thing you've made — and run it through the locker test:

1. **The explain test (gatekeeper).** Can you walk through it line by line, and rebuild the core without AI? If no, either learn it until you can, or don't feature it. Be honest — this is the interview, simulated.
2. **Rewrite the README to show judgment.** Add three things: *what problem it solves*, *one decision you made and why*, and *one thing you changed from the AI's suggestion*. (If you used AI, add the honest one-liner: "I architected, guided, and validated.")
3. **Run the red-flag check (8.2).** Deployed (not just localhost)? Any exposed secrets or unvalidated input (Module 7.6)? Does it show iteration, or look like a first draft?
4. **Write one "learn in public" note** about it — a bug you beat, or why you rejected an AI suggestion. Put it in the README, a gist, or a short post. That's your interview answer, written early.

> **The through-line, delivered:** "AI writes the code now; your job is to out-judge it — and GitHub is where you prove you can." Modules 1–7 built and sharpened the judgment. This module made it *visible* and *credible* to the person deciding whether to hire you. Module 9 gives you the flagship project worth putting in the locker; Module 10 walks it into the room.
